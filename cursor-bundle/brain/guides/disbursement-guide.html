#Overview

What disbursement is — two systems (LOS and LMS Accounting), three rails, three entry points, one converging state machine.

#Two systems, two state machines

A loan's disbursement is owned by two services that talk over Kafka:

LOS — Loan Origination

Owns approval, operator tasks (Manual Disbursement, LAR, Payment Reinitiation), the retry decision, and Kafka push to accounting.

Tables: disburse_loan_process, loan_app, group_details, loan_app_task_details

LMS Accounting

Owns the bank-rail state machine (NEFT v2 / MFT), CRR audit, posting, and async callbacks.

Tables: loan_account, loan_account_events_queue, client_request_response_log

#Three money rails

RailWhat it isLatencySingle or multi-call?
NEFT v2 (default)Two-stage bank API (NEF → NEI) for transfers out to other banksAsync — bank confirms via callback within minutesMulti-call (stage 1 + stage 2)
MFTSingle-shot fund transfer (in-bank or trusted partner)Async — single callbackSingle-call

#Three ways disbursement starts in LMS

Three doors all enter the same orchestration disburseLoan:

  1. Kafka async (production happy path) — LOS publishes to disburse_loan_api_<tenant>.
  2. HTTP sync — operator triggers from Trustt UI.
  3. HTTP async — internal retries / maker-checker resubmits.

#Group loan flow

SHG (Self-Help Group) / JLG (Joint Liability Group) — one parent loan, N members. Parent is the loan-of-record; members receive money.

#Roles

Parent

One account + one loan_account row. Holds the consolidated transfer; the bookkeeping anchor. disbursement_status moves DTFC_SUCCESS → PARENT_SUCCESS → CHILD_SUCCESS → COMPLETED.

Child (member)

One account + one loan_account per member with parent_account_id set. Receives bank-rail money (NEFT/MFT) or cash via LAR.

CLMT queue row

loan_account_events_queue with event_type=CLMT. Per-child bank-leg state tracker — the source of truth per child. Inner data.disbursement_status follows the same ladder as a single loan.

CLB queue row

event_type=CLB. Creates the child loan_account row after CLMT done. Drained by childLoanEventProcessingBatchJob (every 2h).

#NEFT v2 mechanics

Why NEFT v2 is two-stage, what each leg does, and where the inquiry leg fits.

#Why two stages?

The bank's NEFT v2 product is a batch protocol. Stage 1 (NEF) books the payment into the bank's outbound batch. Stage 2 (NEI) submits the batch for actual settlement. Between the two stages, the bank holds the booking but hasn't fired the wire yet — which is why a NEI call without an existing booking returns NDF ("batch details not found").

#Four legs in flight

LegDirectionCRR transaction_typeWhen it fires
NEF (Initiate)System → BankDISBURSEMENT_NEFT_NEFFrom DTFC_SUCCESS
NEI (Submit)System → BankDISBURSEMENT_NEFT_NEIFrom NEFT_STAGE_1_SUCCESS
InquirySystem → BankNEFT_TRANSACTION_INQUIRYWhen prior leg status is uncertain
Bank callbackBank → System(no CRR row — handled by callback processor)Async, bank-driven

#Double-debit guard

Before issuing NEI, the system asks: has a SUCCESS NEI CRR already been written? If yes, NEI is skipped. Combined with deterministic external-ref counters and bank-side dedup, this prevents the same money going out twice.

#NDF rollback — the only backward transition

When the bank's NEF returns NDF — usually because the bank didn't actually create a batch on its side — the loan would otherwise sit forever at NEFT_STAGE_1_PENDING. On 3.3.1.0.1+ the system detects NDF in the raw response and performs a deliberate backward CAS:

#Bank callbacks

How the system listens for bank-side outcomes and reconciles them with in-flight rows.

#Callback shape

Bank delivers async callbacks via HTTPS POST. Each callback contains a list of payments (one batch can carry many) keyed by PAYMENTREFNO = the external-ref the system sent. Each payment carries a codstatus:

codstatusMeaningSystem action
PSuccessful — settledTransition target state forward (STAGE_1_SUCCESS or COMPLETED)
NIn-progress at bank (NEI accepted, settlement underway)For NEI: transition to COMPLETED (NEI accepted is sufficient evidence)
RRejectedMark CLMT row failed; populate error fields
ZReversed by bankMark failed; clear UTR if previously set

#Routing — parent vs child

The callback processor first asks: is the PAYMENTREFNO a parent CRR ref?

  • Yes → parent path: directly transition loan_account.disbursement_status.
  • No → look up CRR by client_reference_number. If transaction_type contains _EXTREF → child path: locate the CLMT row, transition the per-child disbursement_status in its data JSON.

#Orchestration-commit-lag retry

Bank callbacks arrive on Tomcat worker threads independently of accounting orchestration commits. The callback can race ahead of the CLMT row INSERT — under READ COMMITTED, the callback's SELECT would return null. Defence: child callback lookups go through a 5-attempt retry with linear backoff (100/200/300/400ms; ~1s total). The structural fix on 3.3.1.0.1 (CLMT prep-block split that commits CLMT rows in their own REQUIRES_NEW transaction before any bank call fires) closed the root cause; the retry remains as defence-in-depth.

Late-failure semantics: a FAIL callback that arrives after the row is already at SUCCESS is dropped with a log line. Bank's confirmed success cannot be retroactively cancelled by a duplicate-FAIL retry. Operationally rare — but if you see "stuck contradictory state" with conflicting bank callbacks, this is why.

#The cache key contract

The third pipe-delimited field is the Redis cache key that both sides agree on for idempotency:

  • LOS builds it: "disburseLoan" + product_id + "_" + external_ref_number.
  • LOS sets it in Redis ACCOUNTING DB (5) when it pushes to Kafka (value: "in_progress").
  • LMS sets a sibling key dl + cacheKey as its in-progress lock.
  • LMS cleans both up on completion in a finally block.

#Manual Disbursement task

When automated retries fail repeatedly, LOS creates a maker–checker task so an operator can manually correct beneficiary details (or override) and fire disbursement again.

#When the task is created

Trigger: LOS's DisburseLoanProcessor / DisburseGroupLoanProcessor hits retry_count > maxRetryCount. The processor calls CreateUpdateOpsTaskProcessor.createOpsTask() with function_code=CREATE and the task is materialised in two flavors:

Task typeRoleWhat the operator does
MANUAL_DISBURSEMENT_MAKERMakerEnters/corrects beneficiary account details, IFSC, name. Submits.
MANUAL_DISBURSEMENT_CHECKERCheckerReviews maker's entry and approves or rejects.

#LAR task — cash to children

#When the task is created

#What happens on LAR submit

  1. Operator uploads LAR document via task UI.
  2. LOS calls submitLARTask() → task moves to COMPLETED.

#Idempotency & replay safety

Five layers prevent a duplicate disbursement message from sending money twice.

L1

Kafka consumer Redis lock

The dl<productId>_<extRef> key blocks a duplicate Kafka message from entering the orchestration.

L2

Single-thread queue processing

For SHG/JLG, one CLMT row is processed by exactly one orchestration thread.

L3

Cross-pod Redis SETNX

For child bank calls, atomic SET … PX … NX with 10-min TTL prevents two pods firing the same leg in parallel.

L4

Deterministic external-ref

FAIL bumps the counter (fresh ref next call); SUCCESS or UNKNOWN reuses the same ref. Application-level idempotency contract.

L5

Bank-side dedup on external-ref

Bank refuses a second payment with the same ref. Outside our system; the final line of defence.

The counter rule — "FAIL bumps, SUCCESS/UNKNOWN reuses."
If latest CRR is FAIL, next attempt uses a fresh ref (counter + 1). If SUCCESS or UNKNOWN, next attempt reuses the same ref.
That's how a timeout-then-retry doesn't accidentally double-credit: the timed-out call may have actually settled at the bank, so reusing the ref lets the bank dedup the retry. Only after a definitive FAIL does the system know it's safe to ask the bank for a brand-new payment.

#MFT UNKNOWN special-case

If the latest MFT inquiry is UNKNOWN and its counter matches the latest MFT payment counter, the system forces "lastFailed = false" even if the latest payment CRR row is FAIL. Rationale: the FAIL might be transport-only; bumping would issue a NEW payment while the bank may already have processed the first one. NEFT v2 has a different inquiry path and is unaffected.

Acronyms and abbreviations used across this guide and in operator logs.

Loan Origination System — upstream service that approves loans and triggers disbursement.
LMS
Loan Management System — accounting service that owns money-out and the bank state machine.

MFT
Multi-Function Transfer — single-call bank rail for in-bank / trusted-partner payments.

UTR

Client Request Response Log — per-bank-call audit table.
CLMT
Child Loan Money Transfer — queue row tracking a single SHG/JLG child's bank-leg state.
CLB
Child Loan Booking — queue row that creates the child loan_account after CLMT done.
LAR / LEAR

SHG / JLG
Self-Help Group / Joint Liability Group — group loan product types.
INDL
Individual — single-borrower loan product type.
DTFC_SUCCESS
Disbursement Transaction From Customer — initial state after loan-creation accounting completes.
CAS
Compare-And-Swap — atomic SQL UPDATE that only succeeds if the row is in an expected "from" state.
codstatus
Bank callback's per-payment status: P (settled), N (in-progress), R (rejected), Z (reversed).

Deterministic ref sent to bank. FAIL bumps the counter; SUCCESS/UNKNOWN reuses it.

Two-step approval: one user submits, another approves.

function_sub_code
Field on disburseLoan request: DEFAULT / REINITIATE_BANK / PARENT_SUCCESS / ENQUIRY — selects scenario.
