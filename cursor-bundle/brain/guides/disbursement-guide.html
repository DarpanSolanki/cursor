#Overview

Disbursement = moving approved loan money to the borrower’s bank account. Two systems work together; the platform drives the rail (activate → GL CBS → customer bank call → bank callback → COMPLETED → tell LOS). You mostly read status and bank history — you do not manually re-fire every step.

Two live bank rails (NEFT v2 + MFT; NEFT v1 = legacy only), three product shapes (INDL · flat JLG · SHG). CASH is not in production. Flat JLG ≈ INDL (one LAN each); only SHG has parent + children — see §01b.

#Two systems, two state machines

A loan’s disbursement is owned by two services that talk over Kafka (message bus):

LOS — Loan Origination

Where the loan is approved and where operator tasks live (Manual Disbursement; LAR for SHG; Payment Reinitiation). LOS pushes “please disburse” to accounting.

Tables: disburse_loan_process, loan_app, group_details, loan_app__task_details

LMS Accounting

Where money leaves. Owns bank-rail status (NEFT v2 / MFT), CRR (bank-call history — one row per outbound call), ledger posting, and async bank callbacks.

Tables: loan_account, loan_account_events_queue, client_request_response_log (CRR)

#Three ways disbursement starts in LMS

Three doors all enter the same orchestration disburseLoan:

  1. Kafka async (production happy path) — LOS publishes to disburse_loan_api_<tenant>.
  2. HTTP sync — operator triggers from Trustt UI.
  3. HTTP async — internal retries / maker-checker resubmits.

#Product matrix — INDL · JLG · SHG

In one line: INDL = one borrower, one LAN. JLG (flat) = each member has their own LAN like INDL — not a parent group account. SHG = one parent LAN + child LANs (CLMT queue + optional LAR cash).

Verified against accounting mfi_integration_v3.4.2.4 and LOS mfi_integration_v3.4.2.2. The accounting child-flow gate is member_details[] non-empty — not the presence of group_details and not the product label “JLG” alone.

TechOps rule: Flat JLG members follow the same LMS bank ladder as INDL (one LAN per member, no CLMT). Only SHG uses parent + CLMT children + LAR cash fallback. If a guide sentence says “SHG/JLG” for parent–child, treat it as wrong unless it truly means SHG.

NEFT v1 — legacy forensics only

Single-step NEFT (CRR DISBURSEMENT_NEFT, bank ref prefix 03). Production default is NEFT v2 (USE_NEFT_V1=false). Do not treat this tab as the current disbursement path — use NEFT v2 or MFT.

#NEFT v2 mechanics

Why NEFT v2 is two-stage, what each bank-history row means, and why PENDING ≠ “re-fire our call” — often the LAN is waiting on an async bank callback.

#Why two stages?

The bank's NEFT v2 product is a batch protocol. Stage 1 (NEF) books the payment into the bank's outbound batch. Stage 2 (NEI) submits the batch for actual settlement. Between the two stages, the bank holds the booking but hasn't fired the wire yet — which is why a NEI call without an existing booking returns NDF ("batch details not found").

Callback dependency (read this first when status is PENDING): Our outbound call and the bank’s callback are two different events.
  • After NEF sync SUCCESS → LMS writes NEFT_STAGE_1_PENDING and waits for NEF callback before NEFT_STAGE_1_SUCCESS.
  • After NEI sync SUCCESS → LMS writes NEFT_STAGE_2_PENDING and waits for NEI callback before COMPLETED.
  • Bank history (CRR) records our outbound call. The callback does not add another CRR of the same type — it advances status when it matches the payment ref.
  • Stuck PENDING + CRR SUCCESS usually means callback missing / delayed / failed to apply — not “NEF never sent.”

#Double-debit guards

  • Skip NEI when a SUCCESS NEI CRR already exists — for both NEFT_STAGE_1_SUCCESS and NEFT_STAGE_2_PENDING (queue can lag after a successful NEI).
  • Skip ST_NEF when a SUCCESS NEF CRR already exists at DTFC_SUCCESS (defence-in-depth before a second Initiate).

#Bank callbacks

How the bank confirms outcomes after our outbound call. Callbacks advance LMS status — they do not invent money that CRR never recorded.

#Callback shape

Bank delivers async callbacks via HTTPS POST. Each payment is keyed by PAYMENTREFNO = the external-ref we sent on the outbound call. The processor finds that CRR by payment-ref, then tries to move status. Callback outcome codes:

Outcome codeMeaningWhat LMS does (happy path)
P / NEF successBank accepted that stageNEF callback → NEFT_STAGE_1_SUCCESS; NEI success → COMPLETED
NIn-progress at bank (mainly NEI)Code may still move toward COMPLETED on NEI in-progress — treat as bank still working
Fail / reject codesBank rejected after accept attemptOnly applied when LMS is still on the matching PENDING stage; otherwise soft-ignored
TechOps: three stuck buckets
  1. No matching CRR — outbound call never logged → fix/re-fire outbound (after root cause), not “callback ops.”
  2. CRR SUCCESS + still PENDING — outbound done; waiting on callback (or callback lost / failed to apply). Prefer inquiry / wait / logs — do not invent UTR.
  3. Callback arrived but status unchanged — often wrong stage / already moved (CAS reject = “already updated”). Check accounting logs for reject / soft-ignore; do not force COMPLETED.

#Routing — parent vs child

Child / _EXTREF path: SHG CLMTParent CRR path: all products

The callback processor first asks: is the PAYMENTREFNO a parent CRR ref?

  • Yes → parent path: directly transition loan_account.disbursement_status.
  • No → look up CRR by client_reference_number. If transaction_type contains _EXTREF → child path: locate the CLMT row, transition the per-child disbursement_status in its data JSON.

#Orchestration-commit-lag retry

Bank callbacks arrive on Tomcat worker threads independently of accounting orchestration commits. The callback can race ahead of the CLMT row INSERT — under READ COMMITTED, the callback's SELECT would return null. Defence: child callback lookups go through a 5-attempt retry with linear backoff (100/200/300/400ms; ~1s total). The structural fix on 3.3.1.0.1 (CLMT prep-block split that commits CLMT rows in their own REQUIRES_NEW transaction before any bank call fires) closed the root cause; the retry remains as defence-in-depth.

Late-failure semantics: a FAIL callback that arrives after the row is already at SUCCESS is dropped with a log line. Bank's confirmed success cannot be retroactively cancelled by a duplicate-FAIL retry. Operationally rare — but if you see "stuck contradictory state" with conflicting bank callbacks, this is why.

#Repeat reinit & state hygiene

#Idempotency & replay safety

Five layers prevent a duplicate disbursement message from sending money twice.

L1

Kafka consumer Redis lock

The dl + disburseLoan<productId>_<entityType>_<extRef> key blocks a duplicate Kafka message from entering the orchestration.

L2

Single-thread queue processing

For SHG, one CLMT row is processed by exactly one orchestration thread.

L3

Cross-pod Redis SETNX

For child bank calls, atomic SET … PX … NX with 10-min TTL prevents two pods firing the same leg in parallel.

L4

Deterministic external-ref

FAIL bumps the counter (fresh ref next call); SUCCESS or UNKNOWN reuses the same ref. Application-level idempotency contract.

L5

Bank-side dedup on external-ref

Bank refuses a second payment with the same ref. Outside our system; the final line of defence.

The counter rule — "FAIL bumps, SUCCESS/UNKNOWN reuses."
If latest CRR is FAIL, next attempt uses a fresh ref (counter + 1). If SUCCESS or UNKNOWN, next attempt reuses the same ref.
That's how a timeout-then-retry doesn't accidentally double-credit: the timed-out call may have actually settled at the bank, so reusing the ref lets the bank dedup the retry. Only after a definitive FAIL does the system know it's safe to ask the bank for a brand-new payment.

#MFT UNKNOWN special-case

If the latest MFT inquiry is UNKNOWN and its counter matches the latest MFT payment counter, the system forces "lastFailed = false" even if the latest payment CRR row is FAIL. Rationale: the FAIL might be transport-only; bumping would issue a NEW payment while the bank may already have processed the first one. NEFT v2 has a different inquiry path and is unaffected.

#Glossary

Acronyms and abbreviations used across this guide and in operator logs.

LAN
Loan Account Number — 10-digit natural key (e.g. 6009683725).
LOS
Loan Origination System — upstream service that approves loans and triggers disbursement.
LMS
Loan Management System — accounting service that owns money-out and the bank state machine.
NEFT
National Electronic Funds Transfer — bank rail for cross-bank transfers. v2 is two-stage; v1 is legacy.
NEF / NEI
NEFT v2 stage 1 (Initiate) / stage 2 (Submit). Two separate bank API calls.
MFT
Multi-Function Transfer — single-call bank rail for in-bank / trusted-partner payments.
NDF
"No Data Found" / "Batch Details Not Found" — bank inquiry response.
UTR
Unique Transaction Reference — bank-issued ref for a settled payment.
CRR
Bank history row for an outbound call (SUCCESS/FAIL/UNKNOWN). Bank callbacks do not add a NEF/NEI CRR — they advance LMS status. See §06.
Callback wait
LMS at *_PENDING after our call SUCCESS — waiting for bank’s async confirm. Stuck ≠ always re-fire outbound.
ACCTWB / OTHBACCT
Payment mode: ACCTWB → MFT (same-bank style); OTHBACCT → NEFT (other bank).
CLMT
Child Loan Money Transfer — SHG-only queue row for one child's bank-leg state (member_details gate).
CLB
Child Loan Booking — queue row that creates the child loan_account after CLMT done.
LAR / LEAR
Loan Account Receipt — SHG-only cash path for failed/pending children (GROUP / SHGDL).
SHG
Self-Help Group — LMS parent + CLMT children. Only product with PARENT_SUCCESS / LAR child cash.
JLG
Joint Liability Group — after PDC, flat per-member INDIVIDUAL disburse (same ladder as INDL). Not SHG parent–child.
INDL
Individual — single-borrower loan product type.
LOAN_BOOKED
disbursement_status right after activate (loan is ACTIVE) — before GL CBS finishes. Does not mean customer money is paid.
GL CBS
Due-to-FC internal bank leg after activate. CRR types DISB_GL_CBS_INTEGRATION / …_NETOFF. Success → DTFC_SUCCESS. Not the customer NEFT/MFT payment.
DTFC_SUCCESS
disbursement_status after GL CBS succeeds. Customer bank Initiate (MFT/NEFT) can start next. Not “cash paid to borrower yet.”
CAS
Compare-And-Swap — atomic status update that only succeeds if the row is still in an expected “from” state (avoids wrong overwrites).
codstatus
Bank callback's per-payment status: P (settled), N (in-progress), R (rejected), Z (reversed).
External-ref
Deterministic ref sent to bank. FAIL bumps the counter; SUCCESS/UNKNOWN reuses it.
Maker–Checker
Two-step approval: one user submits, another approves.
Replay / Re-fire
Re-publishing disburseLoan (rare / incident). Most stuck cases are wait-for-callback or platform retry — see walker Means / system next, not blind re-fire. Safe only where replay matrix says yes (§15).
disburse_loan_process
LOS-side primary lifecycle table; tracks per-LAN disbursement attempt status and flow.
function_sub_code
Field on disburseLoan request: DEFAULT / REINITIATE_BANK / PARENT_SUCCESS / ENQUIRY — selects scenario.
