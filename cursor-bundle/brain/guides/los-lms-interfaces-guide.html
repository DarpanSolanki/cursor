How LOS and LMS talk to each other

Release train mfi_integration_v3.4.2.4 · LOS 5572a16655 · Accounting (LMS) 112b246770 · Payments 0dae3fc3ed · 20 Jul 2026

1. Purpose

This note lists the interfaces between LOS (loan origination) and LMS (Accounting — the loan books and bank payout). It is meant for managers who need a clear picture of who calls whom, when, and what is different for payment reinitiation, LAR, and manual disbursement.

Evidence is taken only from the pinned train above. Technical file references sit in the Evidence section at the end.

How to read channels

  • Kafka — async money request (disburse_loan_api_) and result (los_lms_disbursement_sync). Message body routes LMS into its disburseLoan orchestration (not a separate money HTTP call).
  • HTTP — sync call/response: enquiry, predisburse bank/mode patch, and (unused on this train) child disbursement-status update.
  • Queue mark C — LMS DB side-effect on loan_account_events_queue (event_type=CLMT, event_status P→C). Triggered by predisburse cash override (live LAR submit), not by the Kafka disburse pair.

2. Picture in words

When a loan is ready to pay out, LOS may patch account details on LMS over HTTP, then publishes a disbursement request on Kafka. Accounting consumes it, runs disburseLoan (book loan / bank payout), and publishes a result on a second Kafka topic. LOS enquires LMS over HTTP for a live LAN view — before/after disburse, during reinitiation, and when creating or regenerating LAR. Separately, LAR submit uses predisburse HTTP only (cash override) to mark matching child CLMT queue rows C — no Kafka money republish.

LOS LMS (Accounting) │ │ │── HTTP predisburse ─────────────►│ bank/mode patch │ (+ LAR cash → CLMT P→C) │ (see §4.4) │── Kafka disburse_loan_api_ ─────►│ run disburseLoan orch │── HTTP getLoanAccountDetails ───►│ status enquiry │ │ │◄─ Kafka los_lms_disbursement_sync│ result (SUCCESS/FAILED) │◄─ Kafka los_lms_data_sync_ ──────│ loan closure only

3. Catalogue — all interfaces

3.1 What LOS uses from LMS

Interface Channel Why / when
disburse_loan_api_ Kafka → LMS disburseLoan Primary money path. LOS asks LMS to create/pay the loan account. Used for auto disburse, manual disburse, and payment reinitiation.
getLoanAccountDetails HTTP Status enquiry — before/after disburse, during reinitiation, and when creating/regenerating LAR.
updateLoanAccountPreDisbursementDetails HTTP Patch bank / disbursement mode on LMS, outside the Kafka money publish.
LAR submit (cash): live path that can mark matching loan_account_events_queue CLMT rows event_status=C (needs mode CASH + pending CLMT for that child + disbursement_status=COMPLETED — see §4.4).
Reinit bank-detail fix: payment_reinitiation_update=true → mode/account only; cash-override (mark C) is skipped.
Manual disbursement checker: payment_reinitiation_update=false → bank/mode update; mark C only if cash-override conditions also match (unusual on this path).
updateChildLoanDisbursementStatus HTTP Sibling LMS API: when child disbursement_status=COMPLETED, marks matching CLMT queue rows event_status=C and updates parent loan_account.disbursement_status. LOS has a client helper, but no live caller on this train — listed for contract completeness; LAR submit uses predisburse above.
Product / overview reads HTTP Support reads (getLoanProductDetails, getLoanAccountOverviewDetails, etc.). Origination and screens — not the money-transfer pipe.

3.2 Reverse updates — LMS back to LOS

Interface Channel Status on this train What LOS does with it
los_lms_disbursement_sync Kafka Live FAILED: LOS writes the failure reason onto the open disburse process (skipped if process already completed / child-success / LAR-task-initiated).
SUCCESS: ignored here by design — LOS finishes via enquiry / its own process completion, not this message.
los_lms_data_sync_ Kafka Live (closure only) Closes / syncs loan-app state when LMS sends event_type=CLOSURE. Not part of the disburse money pair.

3.3 Disbursement Kafka pair (money path at a glance)

Same two topics as above, restated so the request/result pair is obvious.

Topic prefix Direction Role
disburse_loan_api_ LOS → LMS Request: message shape disburseLoan|<json>|<cacheKey> (cache key carries productId_entityType_externalRef)
los_lms_disbursement_sync LMS → LOS Result: external reference, entity_type (echoed from cache key), status, optional error fields

Full Kafka topic name = configured prefix + tenant code, plus optional _{environment} (e.g. disburse_loan_api_<tenant>_uat).

Payments service on this train is not on the LOS↔LMS reinitiation conversation path. Reinitiation is LOS process state plus the same Kafka request into Accounting.

4. How processes use these interfaces

4.1 Auto disburse (happy path)

  1. LOS decides the application can be disbursed and builds a normal disburseLoan payload (function_sub_code=DEFAULT).
  2. LOS publishes to Kafka disburse_loan_api_ (message routes LMS into disburseLoan orchestration).
  3. LMS books the loan / runs bank payout as configured.
  4. LMS publishes los_lms_disbursement_sync. SUCCESS is ignored by LOS here; LOS finishes via enquiry / its own process completion. FAILED can patch a failure reason if the process is still open.

4.2 Payment reinitiation

Retry bank payout when the LMS loan account already exists. Same Kafka pipe as auto disburse; flags tell Accounting “re-run bank lane, do not treat as first create.” Does not use the LAR CLMT mark-C path.

  1. Trigger: Bank payout failed / ops opens a payment-reinitiation journey. LOS process flow = PAYMENT_REINITIATION.
  2. LOS (optional bank fix): Maker/checker may change beneficiary account on LOS. If Accounting tables are updated, LOS calls HTTP updateLoanAccountPreDisbursementDetails with payment_reinitiation_update=true → LMS updates mode/account only (no CLMT event_status=C; cash-override handler is skipped).
  3. LOS → LMS money call: Kafka disburse_loan_api_ → LMS disburseLoan with function_sub_code=REINITIATE_BANK and payment_reinitiation_update=true (both must be present for the consumer skip override).
  4. CLMT queue mark C: not on this path (neither predisburse cash override nor updateChildLoanDisbursementStatus).
  5. What LMS does: Consumer normally skips when loan is ACTIVE and disbursement is already COMPLETED; reinit flags override that skip so the REINITIATE_BANK orchestration branch can re-attempt payout.
  6. What returns to LOS: Kafka los_lms_disbursement_sync — FAILED patches failure reason on the open disburse process; SUCCESS is not how LOS completes the journey.
  7. How LOS finishes: Enquiry via HTTP getLoanAccountDetails and process/retry logic (complete, mark disbursed, or terminal reject / ops task on max retries).
LOS LMS │ │ │── HTTP predisburse (optional) ────────►│ bank/mode only │ payment_reinitiation_update=true │ (no CLMT → C) │── Kafka disburse_loan_api_ ───────────►│ disburseLoan / │ REINITIATE_BANK + flag │ skip override │◄─ Kafka los_lms_disbursement_sync ─────│ FAILED→reason │── HTTP getLoanAccountDetails ─────────►│ finish locally

4.3 Manual disbursement

Ops-driven first (or retry) attempt when auto disburse cannot finish quietly. Money pipe and LMS request flags match auto (DEFAULT) — difference is LOS maker/checker + fail-open task. Not the LAR “one API + mark CLMT C” pattern.

  1. Trigger: Hard fail on auto path, or ops starts Manual Disbursement. LOS opens MANUAL_DISBURSEMENT_MAKER (then checker).
  2. LOS steps: Maker/checker collect or confirm payout details; process flow labelled MANUAL_DISBURSEMENT. Checker may patch LMS bank details via updateLoanAccountPreDisbursementDetails with payment_reinitiation_update=false (bank/mode update; CLMT mark C only if cash-override conditions also match — unusual here).
  3. LOS → LMS money call: Same Kafka disburse_loan_api_ → Accounting disburseLoan with normal function_sub_code=DEFAULT (no REINITIATE_BANK).
  4. CLMT queue mark C: not the intentional manual-disburse mechanism (that LAR cash / sibling-status path is §4.4).
  5. What LMS does: Runs the standard disburseLoan booking / bank path as for auto.
  6. What returns to LOS: Same los_lms_disbursement_sync contract (FAILED→reason; SUCCESS not process-complete).
  7. How LOS finishes: Enquiry / process completion on success; on hard fail, create/reopen MANUAL_DISBURSEMENT_MAKER rather than a silent batch-only retry.
LOS LMS │ │ │ MANUAL_DISBURSEMENT_MAKER → checker │ │── Kafka disburse_loan_api_ ───────────►│ disburseLoan │ DEFAULT flags │ (same as auto) │◄─ Kafka los_lms_disbursement_sync ─────│ │ success → enquiry/process done │ │ hard fail → MANUAL_DISBURSEMENT_MAKER │

4.4 LAR (Loan Advice Report)

LAR is a LOS document + ops-task journey for group (SHGDL) children that still need payout attention. There is no dedicated “LAR Kafka money” topic. LMS is involved via shared HTTP APIs.

One Accounting API + mark CLMT queue C (live on this train): on LAR submit, LOS calls HTTP updateLoanAccountPreDisbursementDetails per selected child (mode from payload or default CASH; disbursement_status=COMPLETED). LMS runs updateLoanDisbursementModeDetailsProcessor → DisbursementClmtCashOverrideHandler when mode is CASH and pending loan_account_events_queue rows with event_type=CLMT match the child (filler2 = child external ref). Matching rows get event_status=C and message “Manually Completed through LAR”. Parent disbursement status may advance to COMPLETED when no CLMT rows remain P.

A — Create / regenerate LAR (document + task)

  1. Trigger: Group ops creates or regenerates LAR (generateLarDocument / create LAR ops task).
  2. LOS → LMS: HTTP getLoanAccountDetails (enquiry) for the group; children already COMPLETED are skipped for the document/task payload.
  3. CLMT mark C: none on this step.
  4. What LMS does: Returns current parent/child LAN disbursement picture.
  5. What returns to LOS: Enquiry response only (no disbursement sync for this step).
  6. How LOS finishes: Builds LAR (Jasper/DMS), creates post-disbursement document-upload task, sets disburse process to LAR_TASK_INITIATED (LOS DB).

B — Submit LAR (cash override → CLMT completed)

  1. Trigger: Ops submits the LAR task (SUBMIT_LAR) with customer_lar_details (children to treat as manually completed / cash).
  2. LOS → LMS (the one write API): For each listed child, HTTP updateLoanAccountPreDisbursementDetails (disbursement_mode from payload or default CASH, disbursement_status=COMPLETED; no payment_reinitiation_update).
  3. CLMT queue mark C — yes, when conditions match: table loan_account_events_queue, event_type=CLMT, column event_status → C (was P); embedded JSON cleared of external error fields and stamped for LAR manual completion. Sibling API updateChildLoanDisbursementStatus can do the same mark in LMS but has no LOS caller on this train.
  4. What LMS does: Persist new disbursement mode details; mark matching pending CLMT events completed; optionally set parent loan_account.disbursement_status=COMPLETED when no CLMT remain pending.
  5. What returns to LOS: Synchronous HTTP success/fail on predisburse (not the disburse Kafka sync pair).
  6. How LOS finishes: Completes the LAR task / group task, updates LAR document metadata, moves disburse process to LAN_FETCH_IN_PROGRESS (then subsequent LOS fetch/enquiry steps as configured).
LOS LMS │ │ │── SUBMIT_LAR │ │── HTTP updateLoanAccount │ │ PreDisbursementDetails ─────────────►│ mode=CASH (+ COMPLETED) │ (per child in LAR details) │ │ │── loan_account_events_queue │ │ event_type=CLMT │ │ event_status P → C │◄─ HTTP success ────────────────────────│ │ complete LAR task / advance process │

5. What changes in the request (money slide)

All three variants use the same Kafka topic. The message body is shaped for LMS orchestration API name disburseLoan (Kafka carrier — not a money HTTP call). Differences are in a handful of fields.

Field Normal / auto Payment reinitiation Manual disbursement
function_code DEFAULT DEFAULT DEFAULT
function_sub_code DEFAULT (or a stage code on internal retry) REINITIATE_BANK DEFAULT
payment_reinitiation_update Absent / false true Absent / false
LOS flow label (not an LMS topic) DEFAULT PAYMENT_REINITIATION MANUAL_DISBURSEMENT
Kafka topic disburse_loan_api_ (same pipe)
Typical ops task on hard fail Manual maker (also for DEFAULT flow fail-open) Payment-reinitiation reject / terminal handling MANUAL_DISBURSEMENT_MAKER

Short rule: reinitiation = same pipe + REINITIATE_BANK + payment_reinitiation_update=true. Manual = same pipe + LOS ops wrapper; request flags look like normal DEFAULT.

6. Important notes

Success sync does not complete the LOS process. By design, los_lms_disbursement_sync only patches failure reasons. Success completion happens through enquiry / process logic.

Blank entity_type on result sync → LOS ignores the message. LMS puts entity_type on the result from the disburse cache key (LOS builds disburseLoan{productId}_{entityType}_{externalRef}). If that segment is blank, LOS no-ops and the failure reason is not updated.

LAR CLMT mark-C is predisburse cash override, not Kafka disburse. Live path: updateLoanAccountPreDisbursementDetails → loan_account_events_queue.event_status = C for matching CLMT rows when mode is CASH, status is COMPLETED, and a pending row matches the child. Payment reinitiation and manual disbursement use the Kafka money pipe and do not rely on that mark for their money step.

7. Glossary

LOS
Loan Origination System — where applications are captured and disbursement is triggered.
LMS
Loan Management System — in this platform, the Accounting service that owns loan accounts, GL, and bank payout.
LAN
Loan Account Number — the LMS account identifier after booking.
LAR
Loan Advice Report — LOS group document/task journey. Enquiry via getLoanAccountDetails; submit cash override via updateLoanAccountPreDisbursementDetails marks CLMT queue C.
CLMT
Child Loan Money Transfer — loan_account_events_queue.event_type. event_status P=pending, C=completed.
Kafka
Async message bus. Producer writes; consumer processes later. Used for disbursement request and result.
API / HTTP
Synchronous request/response call between services (enquiry, predisburse patch, unused sibling status API).
disburseLoan
LMS orchestration API name. On the money path it is invoked by the Kafka consumer from the disburse_loan_api_ message — not by a separate LOS→LMS money HTTP call.
function_sub_code
A routing flag on the request that tells LMS which branch of the disbursement flow to run (DEFAULT vs REINITIATE_BANK, etc.).
Payment reinitiation
Retry of bank payout after the LMS account already exists — overrides the ACTIVE+COMPLETED skip. Same Kafka pipe; no LAR CLMT mark-C.
Manual disbursement
Ops-driven disbursement path with maker/checker on LOS; still uses the same LMS Kafka pipe and DEFAULT request flags.
