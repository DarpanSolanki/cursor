# System Activation & Wiring Layer — what makes a flow EXIST and be reachable

> The brain docs and KG map **business flows** (Request → processors → tables → GL) and the **runtime** path. This doc maps the **other dimension** the substrate was blind to: the **activation/bootstrap/wiring layer** — the things that must be wired for a flow to be reachable *at all*. A feature can have correct Java, a green build, an orchestration `<Request>`, and an `api_master` row, and still **never run** because one activation point was missed. This is the layer that bit the DPIC EOD jobs (coded, never wired into the loader → never registered → never ran). All anchors are `file:line`-verified (2026-06-12).
>
> **The unifying model:** this platform activates features through **dynamic runtime bean registration + DB seed rows + orchestration-XML opt-in**, NOT static `@Bean`/annotations alone. **Most activation misses fail SOFT** — silent no-op, `null`, or fail-open — which is exactly why they're invisible in flow docs and why engineers (and past sessions) get burned. When debugging "why doesn't X run / why is X stale / why wasn't X checked", trace the activation chain, not just the flow.

## Master table — the 14 activation mechanisms

| # | Mechanism | What makes it EXIST | Fail mode if missed | The common miss |
|---|---|---|---|---|
| 1 | **Batch job registration** | a `*JobLoader` (invoked by `Loader.initJobs @PostConstruct`) calls `<Job>BatchConfigService.buildJobForTenant()` → `setUpJobAdvanceV2` → registers the Job bean + auto-seeds `mfi_batch.batch_job`/`batch_schedule` | **SILENT** — no row, no schedule, job never fires, no error | not wired into the loader (DPIC) |
| 2 | **Batch placeholder bean** | `BatchJobPlaceholderConfig` `@Bean(name=jobName) @ConditionalOnMissingBean` stub `Object` per job name | **LOUD** — `NoSuchBeanDefinitionException` → service won't start | new job, no placeholder added |
| 3 | **Orchestration `<Request>`** | a `<Request name="x">` block in a `*_orc.xml`, loaded by `OrchestrationXMLParser` at startup, keyed `tenant_requestName` | **LOUD** — `13014` "Orc XML config not present" | wrong file / wrong `tenant` attr |
| 4 | **Processor/validator beans** | each `<Processor bean="b">` resolves `applicationContext.getBean("b")` at dispatch | **LOUD** — `NoSuchBean` → `220000` fatal | bean name ≠ XML `bean` attr |
| 5 | **api_master / ServiceRegistry** | `api_master ⋈ service_master` row (platform_master), loaded `@PostConstruct` into `ServiceRegistry`; only for **internal/cross-service `<API>`** & scheduled-job calls | **LOUD** — `13022` "configure if missed in api_master" | new internally-called Request / job |
| 6 | **Kafka consumer wiring** | a `<Consumer>` block in `MessageBroker.xml` + a `@Component` bean of that name; built by `NovopayMessageBrokerBuilder` on `ApplicationReadyEvent` | **SILENT** — no thread starts, messages pile up | XML block or bean name missing |
| 7 | **Scheduler trigger** | for batch: the `batch_schedule.cron_expression` row (auto-seeded by #1) read by the **batch service** `AutoScheduler` | **SILENT** — registered but never armed | batch service not restarted / wrong cron |
| 8 | **Event-queue drain** | `loan_account_events_queue` rows (`event_status='P'`) drained by `ChildLoanEventProcessingBatchJob` + the SOF `childLoanEventsProcessingProcessor`, routed via `EVENT_TYPE_ORC_API_MAP` | **SILENT** — child event stuck `P`, parent never syncs | event_type not in the map / drain job not registered (#1) |
| 9 | **Cache eviction pairing** | every write path to a `@Cacheable` value must carry `@CacheEvict`/`NovopayCacheClient.remove` | **SILENT** — stale value served (forever if the cache manager has no TTL) | a write path that bypasses the evicting DAO method |
| 10 | **Tenant context** | `ThreadLocalContext.setTenant` at every entry (HTTP, async thread, Kafka, batch) | **LOUD** `333` if null — or **WORSE**, leaked tenant from a pooled thread → cross-tenant read | new thread/async path without propagation |
| 11 | **Flyway migration** | a `Vxxxx__*.sql` in the **right module dir** (per-schema, per-module version namespace) | mixed — duplicate version = LOUD; wrong module = SILENT (applies to wrong/no schema) | reusing a number / wrong band (`V000*` vs `V9000*`) |
| 12 | **Gateway authz mapping** | `api_usecase_mapping` (gateway) + `usecase`/`permission`/`role__permission__mapping` (authorization) | **SILENT FAIL-OPEN** — no `api_usecase_mapping` row ⇒ permission check **skipped**, request forwarded unchecked | new secured Request, no mapping |
| 13 | **Audit / notification / DMS / masterdata / config opt-ins** | per-flow `<Audits>` block; notification template rows; `product_document_master` type row; `code_master` seeds; `@NovopayConfig` default + override row | **SILENT** — audit no-op / notification dropped / null lookup / flag runs at default | assuming these are automatic |
| 14 | **Request/response templates (JTF)** | `deploy/application/templates/{request,response}/product/<Request>_*Template.json` — a `{field:{class,type}}` schema the navigation/gateway layer uses to marshal named inbound fields into the `ExecutionContext` and shape the response | **MIXED** — a *guarded* field (e.g. `op_code`) → LOUD throw; an *unguarded* field → SILENT null/dropped | new Request, template not added (DPIC #2) |

Legend: **LOUD** = fails fast (exception / won't boot) — easy to catch. **SILENT** = no error, feature just doesn't happen — the dangerous class, and the reason this doc exists.

## 1. Batch job registration (the deepest, most-missed chain)

A coded batch job does **not** run because the Reader/Processor/Writer exist. It runs only if, at the owning service's startup, a loader calls its config service. Full chain (accounting canonical):

```
Loader.initJobs() @PostConstruct        (batchnew/common/Loader.java:252; gated isBatchJobsEnabled() :256)
  └─ per tenant (getAllTenants → ThreadLocalContext.setTenant)   :259-262
       └─ <domain>JobLoader.loadJobs(tenant)        e.g. LoanSystemDailyJobLoader :372
            └─ <Job>BatchConfigService.buildJobForTenant()       (DpiBilling…:80, InterestAccrualCalc…:83)
                 └─ parallelCommonBatchJob.setUpJobAdvanceV2(cfg, setup, steps)
                      ├─ AbstractBatchJob.registerJobMultiSteps   (infra-batch …:361)
                      │    ├─ beanFactory.registerSingleton(jobName, job)  → "Successfully registered job: {}"  (:384-385)
                      │    └─ batchDBHandlerService.createBatchJob(name, params)        (:369)
                      │         └─ INSERT <tenant>.batch_job ; then (because group_code present)
                      │            createBatchGroup → addJobToGroup → createBatchSchedule(cron)   (BatchDBHandlerService:199-205)
                      └─ (multi-node path → parallelKafkaBatchJob)
```

**Key facts / footguns:**
- **The job self-seeds its own `batch_schedule`/cron** from `getJobSetupParameters()` (`name`, `code`, `group_code`, `priority`, `cron_expression`). You do **not** hand-insert schedule rows. If `group_code`/`cron_expression` are omitted, the `batch_job` row is created but **no `batch_schedule`** → registered but never scheduled.
- **Registration is per-tenant** (DB writes target the tenant-prefixed `mfi_batch` schema).
- **Loaders per service** (each is a `@PostConstruct` bootstrap; guard inconsistency matters): accounting `Loader.java:252` (gated `isBatchJobsEnabled`); actor `actor/batch/Loader.java:83` (**no guard**); los `los/batch/Loader.java:120` + IRR/Risk/Ckyc/Expiry/AuditMonthly loaders (only some gated); payments `Loader/Loader2/Loader3` (**no guard**); task `batch/Loader.java:49`; masterdata `:35`; notifications `:33`; **authorization has no bootstrap at all**. → "why did this job still run when batch is disabled" = the guard only covers a subset.
- **The trigger lives in a SEPARATE JVM** (`novopay-platform-batch`): `AutoScheduler.onLoadScheduleGroups @PostConstruct` reads `batch_schedule`, arms a Spring `ThreadPoolTaskScheduler` with `GroupCronTrigger(cron)`; on fire → `DirectJobExecutor` → `callInternalAPI(jobName)` (HTTP) → the owning service's `<Request>` `BATCH` branch. So a registered job still needs (a) the batch service running and **restarted** to pick up a new schedule row, and (b) an `api_master` row to route the cross-service call (#5). **`AutoScheduler` arms the first tenant only at boot** (gaps-and-risks GAP-046).
- Cross-ref: the batch-service side is documented in [`../accounting/03-batch-dependency.md`](../accounting/03-batch-dependency.md); this doc adds the **accounting-side registration + placeholder** half it omitted.

**To add an EOD/batch job so it ACTUALLY runs — touch ALL of:** (a) Reader/Processor/Writer/`BatchConfigService` with `getJobSetupParameters()` carrying group_code+cron; (b) `<Request>` with a `BATCH` branch in the orc XML; (c) wire the config service into the right `*JobLoader` (**the DPIC miss**); (d) `BatchJobPlaceholderConfig` stub bean (#2); (e) `api_master` row (#5); (f) the batch service restarts to arm the new schedule. (a)–(e) are manual; the `batch_group`/`batch_schedule` rows are **auto-seeded** by (c) at boot.

## 2. Batch placeholder beans — `BatchJobPlaceholderConfig`

Each batch `<Request name="x">` resolves a bean named `x` at **context-init** (orchestration parse), but the real Job bean is only registered later at `@PostConstruct` (#1). `BatchJobPlaceholderConfig` reserves the name with `@Bean(name="x") @ConditionalOnMissingBean(name="x") → new Object()`. The real Job overlays it in the `JobRegistry` (`AbstractBatchJob.safeRegisterJob` catches the duplicate-singleton and re-registers via `ReferenceJobFactory`). Same pattern in **7 services** (accounting, actor, masterdata, notifications, payments, task, los). **Missing placeholder for a new job → the service fails to boot** (`NoSuchBeanDefinitionException`). This is mechanism #1's fail-loud twin.

## 3–5. Orchestration Requests, dispatch, and API routing

- **Load/parse** — `OrchestrationXMLParser` (infra-navigation) is an eager singleton (`InitializingBean.afterPropertiesSet`); reads the whole `deploy/application/orchestration` dir in **undefined `File.listFiles()` order**; keys each Request `tenantAttr + "_" + name`, **blank tenant → `"product"`**. Lookup `getRequestFromOrcXML(tenant, name)` tries `<tenant>_name` then walks `novopay.orchestration.precedence.order` (accounting = `mfi,product`), else **`13014`**. Duplicate Requests across files **only collide if same `(tenant,name)`** — accounting's 14 apparent dups are tenant-namespaced (`mfi_disburseLoan` vs `product_disburseLoan`) and don't collide; but a real same-tenant dup would resolve **non-deterministically** (undefined file order) — a latent footgun.
- **Dispatch** — `ServiceGatewayController POST /api/{ver}/{name}` → `RequestProcessorImpl` (sets tenant; async branch returns immediately if `isAsync="true"`) → `ServiceOrchestrator.processRequest` = validators → processors → success → audits → (finally) alerts. `ProcessorOrchestrator` resolves each `<Processor bean="b">` via `applicationContext.getBean("b")`; missing/typo bean → **`220000`** fatal. `<Control>` predicate false → processor **silently skipped**.
- **Transaction boundary** (well-covered in [`transaction-model.md`](transaction-model.md)): implicit (whole list in one `REQUIRES_NEW`) unless `explicitTxnMgmt="true"` / `httpMethodType="get"` / internal-explicit — then only `<Transaction>` blocks commit. **Same-service internal calls force `explicitTxnMgmt=true`**.
- **API routing** — `<API name="x">` → `NovopayInternalAPIClient.callInternalAPI` 3-way router: cache-gateway / **same-service in-process** (`checkIfSameServiceCall` compares `serviceRegistry.getAPIServiceName(x)` to `novopay.service.name`) / **cross-service HTTP** (URL = `service_master.endpoint` of the owner). `ServiceRegistry` loads `api_master ⋈ service_master` (platform_master) at **`@PostConstruct`**, lazy-reloads on miss; **no row → `13022`** "Invalid API Endpoint … configure if missed in api_master". The external gateway entry does **not** need api_master (dispatches off the local orc map); only `<API>`/scheduled-job calls do. Error-code legend: **`13014`** orc missing · **`220000`** bean missing · **`13022`** api_master missing.

## 6–8. Async: Kafka, schedulers, the event-queue

- **Kafka** — `NovopayMessageBrokerBuilder.build()` is an `@EventListener(ApplicationReadyEvent)`; per `<Consumer>` × per tenant it does `context.getBean(consumerNode.getBean())` and spawns N threads. **Runtime topic = `topicPrefix + tenantCode [+ "_" + env]`** (config prefix ≠ runtime topic); group similarly. **`message.broker.bootstrap.servers` unset → the whole broker layer silently no-ops.** To add a consumer: `<Consumer>` block in that service's `MessageBroker.xml` + a `@Component implements NovopayMessageBrokerConsumer` whose **bean name == the XML `<bean>`**. Missing bean → that one consumer silently absent. Per-service consumers are inventoried in [`event-registry.md`](event-registry.md) (accounting `lmsMessageBrokerConsumer` on `disburse_loan_api_`; los `disbursementSyncConsumer` on `los_lms_disbursement_sync`; payments 8; actor 4; notifications 5 sink-only; task 3).
- **Schedulers (only these exist)** — exactly **two** Spring `@Scheduled` in the whole workspace (http-client connection eviction; api-gateway session purge). **No `@Scheduled` in accounting/payments/actor/los/task; no Quartz.** All LMS/EOD periodic work fires via the batch-service `AutoScheduler` (#1/#7). Task-service "cron" strings are **job-setup params** registered into `batch_schedule`, fired by the batch service — not local `@Scheduled`. (Detail: [`scheduler-registry.md`](scheduler-registry.md).)
- **`loan_account_events_queue` fan-out** (SHG/JLG child spine) — parent processors INSERT rows `event_status='P'`, `event_type ∈ {CLB,CLMT,FCL,REP,WAIVER,…}`; `LoanAccountEventsQueueEntity.EVENT_TYPE_ORC_API_MAP` routes each type → a child Request. **Two drains** run the SOF orchestrator per row: the inline `childLoanEventsProcessingProcessor` (group_mfi_orc.xml) and the scheduled `ChildLoanEventProcessingBatchJob` (a #1 batch job). Idempotency = the `P→C` flag; a stuck child is a `P` row whose orchestration threw (exception parked in `filler1`). **An `event_type` not in the map, or the drain job not registered (#1), → the event silently never processes and the parent never syncs.** Deep table doc: [`../accounting/db-code-map/tables/loan_account_events_queue.md`].

## 9–13. The quietly-fatal cross-cutting opt-ins

- **Cache** — cache managers (`NovopayCacheConfiguration`: `accountingCacheManager` DB5, `authorizationCacheManager` DB4/24h, masterdata DB1, notification DB2, los DB8, default DB0) **auto-create cache names on first access** (no pre-registration). Keys namespaced by `customKeyGenerator` (env+service+class+method+params). **Every** mutating path must pair `@CacheEvict(allEntries=true)` / `NovopayCacheClient.remove`; managers with **no TTL** (accounting/masterdata/los/default) serve **stale forever** if an evict is missed. Wrong `cacheManager=` qualifier → writes to the wrong Redis DB → silent permanent miss. (Registry: [`redis-key-registry.md`](redis-key-registry.md).)
- **Tenancy** — `ThreadLocalContext` (`ThreadLocal<PlatformTenant>`) set at HTTP entry (`RequestProcessorImpl`), async re-propagation (`ServiceOrchestrator`), Kafka consumer, and batch loop. `getTenantCode()` null → **`333`** fatal; a spawned thread without propagation either throws `333` or **leaks a pooled thread's previous tenant → cross-tenant read/write**. (`currentUserId` is a `static` field — concurrency smell.) (Runbook: [`../runbooks/tenant-bootstrap.md`].)
- **Flyway** — migrations live in `novopay-platform-initial-setup/flyway/sli/<module>/sql/`, **one schema per module** (`flyway.schemas=mfi_<module>`), so **version numbers are PER-MODULE, not global** (accounting and actor can both have `V9000001`). Within a module, `sli/common` + `<module>/sql/{product,mfi}` merge into one ordered sequence: **`V000*` = base/product band, `V9000*` = MFI tenant-overlay band** (the `V9` prefix sorts after, so overlays apply last). Pick-next rule: target schema → fixes the module dir + band → increment the max **in that band**. Reusing a number = duplicate-version error (loud); wrong module dir = applies to the wrong/no schema (silent "table not found" later).
- **Gateway authz** (security-relevant) — a secured Request needs `api_usecase_mapping` (gateway) **and** `usecase`/`permission`/`role__permission__mapping` (authorization). **No `api_master` row → `13022` unroutable (loud). But no `api_usecase_mapping` row → `AuthorizationCheckFilter` `if(entity != null)` skips the check → request forwarded UNCHECKED (silent fail-OPEN).** Missing role grant → `274002` 403.
- **Audit** — `AuditOrchestrator` emits to Kafka `audit_<tenant>` **only if the orchestration XML declares `<Audits><Audit>…`**; ~⅔ of accounting Requests declare none → silent no-op (action never appears in audit search). Not automatic.
- **Notification / DMS / masterdata / config** — notification needs `code__notification_code__mapping` + `notification_message` (+ `email_template`) rows or the message is dropped/NPEs (no default text). DMS `document_master` is a dumb UUID blob store; the real type registry is masterdata `product_document_master` — missing row → orphan blob + upstream null. `code_master` lookups return **null/empty silently** if unseeded. `@NovopayConfig`/`ConfigValue` resolves per-tenant cache→API→`defaultValue`; a missing row + wrong default → feature **silently runs in its default/off state** (the CBC=0 class — [[feedback_config_resolution_rca]]).

## 14. Request/response templates (JTF field-mapping) — the marshalling opt-in

Every `<Request>` has a pair of templates: `deploy/application/templates/request/product/<name>_requestTemplate.json` and `…/response/product/<name>_responseTemplate.json`. Each is a flat schema declaring the **named fields** the platform extracts from the inbound JSON into the `ExecutionContext` (and shapes on the way out): `{"<Request>": {"<field>": {"class":"SMPL","type":"String|ARR|…"}}}`. The infra navigation/gateway layer applies the request template at dispatch; **a field absent from the template is never placed in the `ExecutionContext`** (the loader class lives in the infra-navigation jar, not the service src).

**Why it bit DPIC (the second miss):** all 3 DPI batch processors read `executionContext.get("op_code")` and `throw NovopayFatalException("op_code must not be empty or null!")` when blank (`DpiAccrualCalculationBatchProcessor.java:51`, booking `:59`, billing `:60`). With no request template, the standard nested batch payload `{"request":{"dpiAccrualCalculation":{"job_time":…,"op_code":"START"}}}` never maps `op_code`/`job_time` into the context → the guard fires every run. Fixed by adding the 6 templates (origin `6bf108847`), each mirroring `interestAccrualCalculation_requestTemplate.json`.

**Fail mode is MIXED:** a field the processor *guards* (op_code) → LOUD fatal; an *unguarded* field → SILENT (reads null/default, logic quietly wrong). A missing template is therefore not always a clean error. Add the request+response pair for every new Request and mirror the closest sibling's template.

## New-feature activation checklist (use alongside the [feature-development-playbook](../guides/feature-development-playbook.md) 12-layer matrix)

For any new feature, after the business code, ask **"what makes each piece reachable?"**:

- [ ] Orchestration `<Request>` in the right `*_orc.xml` (correct `tenant`/`isAsync`/`explicitTxnMgmt`) — else `13014`.
- [ ] Every `<Processor>/<Validator>` bean exists by name — else `220000`.
- [ ] `api_master` row if the Request is called internally/cross-service or as a scheduled job — else `13022`.
- [ ] **Batch job:** `BatchConfigService.buildJobForTenant()` **wired into a `*JobLoader`** + a `BatchJobPlaceholderConfig` stub bean + group_code/cron in setup params. (The DPIC class of miss — silent.)
- [ ] Kafka: `<Consumer>`/`<Producer>` in `MessageBroker.xml` + matching bean name.
- [ ] **Request/response templates** (`deploy/application/templates/{request,response}/product/<name>_*Template.json`) for every new Request — else named fields (e.g. `op_code`, `job_time`) never reach the `ExecutionContext` (guarded field → loud throw; unguarded → silent null). Mirror the closest sibling. (The DPIC #2 miss.)
- [ ] Cache: `@CacheEvict`/`remove` on **every** write path to a cached value; correct `cacheManager`.
- [ ] Tenant set on any new thread/entry point; cleared after.
- [ ] Flyway file in the **right module dir + band**, next free version.
- [ ] Secured API: `api_usecase_mapping` (else fail-OPEN) + usecase/permission/role grant.
- [ ] Opt-ins as needed: `<Audits>` block, notification template rows, `product_document_master` type, `code_master` seeds, `@NovopayConfig` default + override row.
