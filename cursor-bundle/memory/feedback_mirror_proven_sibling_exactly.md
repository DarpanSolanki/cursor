2. **Right sibling = INTEREST, not DPD.** I FIRST patched the window to mirror DPD (`getEarliestInstallmentDateWithUnpaidDpdComponents`) — **the user rejected that** ("fix for DpiAccrualCalculationBatchService should NOT be how DPD is doing; refer the interest calculation job"; "Product told DPI will be mostly as the interest component is handled"). The correct sibling is **`InterestAccrualCalculationBatchService` in full**: `getAccrualStartDate` = last accrual `end_date` (else disbursement); a segmented `while` loop with `getAccrualEndDate = min(now, next due date, next month-end)`; **carry-over** of the fractional remainder (`tCarryOverAmount`) so rounding lands once at the month-end/due boundary, not per day; and the accrual is keyed to the **next due installment** so it BILLS on the *next* installment, not the overdue one (UD + sample: May accrual billed on 05-Jun). Mirroring interest naturally handles "accrue only when overdue" (base=0 → skip) — DPD's earliest-overdue query is unnecessary. My earlier "overdue→DPD" reasoning was WRONG; don't repeat it.
